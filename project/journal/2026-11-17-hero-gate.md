# 2026-11-17 upload refuses a zone with no hero (opus-hero1)

Jake, 2026-11-17 ~14:32 Cancún: "in zone select there are zones without
hero images that's bad, that should be failing at either the sharddev cli
or the api-server level or both." Meta HERO-GATE HG2.

`wildshard upload` now runs `cli/upload/hero-gate.ts` before a byte is
sent. The card is the discovery mount's `data.card` (what the cook serves
a placed zone's card), else the manifest's, else the presentation's. It
refuses `[hero-missing]` (no card), `[hero-generated]` (the `data:`
placeholder `wildshard new` gives), `[hero-image]` (an image the shard
file does not carry, or not PNG/JPEG/WebP) and `[hero-size]` (not thumb
640x360, portrait 804x1626, landscape 1600x900). Each names the fix,
`wildshard hero <shard> --base <url>`. The rules and the order are
api-server's commit gate (`src/server/shardfile/hero-gate.ts`, 2f4f308
and b804d06), and `image-size.ts` is a copy of api-server's.

A stale hero is still refused at build (`hero-stale`, `assertHeroCurrent`),
which `wildshard check` already runs; a shard file carries no stamp, so
upload cannot judge freshness itself.

The test shard file (Template 2) had one 600x1400 image for all three
slots, which the gate refuses. `test/helpers/hero-fixture.ts` swaps its
discovery card for three generated PNGs at the hero sizes, mounted beside
it, shaded by seed so each revision's hero differs. The test tar writer
learned ustar's prefix field for the longer mount paths.
