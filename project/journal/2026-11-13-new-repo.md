# 2026-11-13: `wildshard new` writes a shard repo (meta SHARD-AUTHORING SA16)

> Written by: Claude

- `new <dir>` writes a whole single-shard repo: the shard source at
  `src/` (J317), plus `package.json` (sdk, shard-format, engine and
  `three` pinned exactly as the installed sdk pins them, so the repo
  installs one copy; `packageManager` pnpm 10.34.9 for SA39's list;
  `version` 0.0.1, which upload reads), `tsconfig.json`, `.gitignore`,
  `.npmrc` and its own README. The template's README (sharddev notes)
  no longer ships.
- `--template sdk|blender`, a flag only, default `sdk`. An unknown name
  refuses before writing (`new-template`). `blender` refuses as not
  built yet: shard-format ships Brasscap Mesa only as a built shard
  file (`corpus/brasscap-mesa`), and turning a built folder back into a
  `shard.config.ts` is real work, not a copy.
- `shardSource.ts`: the verbs find a source at `src/` or a repo's one
  `src/shards/<slug>/`; a `src/` source is named by its manifest slug,
  so `new <dir> <slug>` with a slug unlike the folder builds (it used to
  hit `project-folder-slug`), and its output goes to the repo's
  `public/shardfiles/`. The image root and the hero stamp use the same
  slug name.
- Proof: `npm pack` of this checkout into `tmp/opus-sa16`, `new` with a
  folder unlike the slug, the sdk pointed at the tarball, `pnpm install`
  then `pnpm exec wildshard check .`: pass. The CI tests that call `new`
  now point it at a repo and edit `src/`.
- Left: `tsc` over a new repo still reports the template's own latent
  type errors and engine's `.ts` sources (the tsconfig is for editors).
